## 1. What we're building

An internal web portal for **Evident** to manage service cases for microscopes sold to Evident's
clients. Evident contracts external customer-service providers ("service trackers", e.g. *Oneservice
France*, *Oneservice Italy*) who handle returns, repairs, and maintenance. The portal is where Evident
staff and these external partners track and collaborate on cases.

Build and run **fully local first**. No deployment concerns yet.

## 3. Core concepts

- **Region** — geographic grouping (e.g. France, Italy). *Cases belong to one region.* List: [FILL IN].
- **Service Tracker** — an external provider org (e.g. Oneservice France). **Each service tracker belongs
  to a region** (`region_id`). A tracker's cases inherit/validate against that region. A partner user
  belongs to [one? / many?] trackers. Initial list: [FILL IN].
- **Case** — the central object. Has **stable fields** (real columns) plus **dynamic fields** (§5).
- **Dynamic field** — a case property the business adds, removes, reformats, or restricts over time.
  Governed by `field_definitions`, stored per-case in JSONB.
- **Case event** — an append-only audit record; every case change writes one. Status changes are flagged.
- **Notification** — a per-user alert generated by case activity (status change, comment, assignment,
  new document). See §9.

## 5. Dynamic fields (requirement — read carefully)

Do **not** model changing case properties as fixed columns.

- **Stable columns** on `cases`: `case_number`, `status`, `region_id`, `service_tracker_id`,
  `created_by`, `created_at`, `updated_at`.
- **Dynamic values** live in a `data JSONB` column on `cases`.
- **`field_definitions`** describes every dynamic field: `key`, `label`, `data_type`
  (text/number/date/select/…), `options`, `status` (active/deprecated), `visible_to_roles` (array),
  `sort_order`, `created_at`.
- App reads `field_definitions` to decide **which fields to render, how, and to whom**.
- Deprecating a field **keeps** existing values. Per-**field** visibility is enforced server-side
  (Supabase RLS handles per-**row**; per-**field** needs app-layer / DB-view help).

The properties in §6 below are the *current* field set — model the volatile ones as dynamic fields.

## 6. Completed case fields & the Case Detail design

### 6.1 Field inventory (current)

Group the 16 properties into logical sections (this grouping drives the Detail layout):

| Section | Fields |
|---|---|
| **Summary / header** | ID, Case number, Service order, Job type, Status |
| **Customer** | Customer name, Customer number, Customer contact person, Customer phone, Customer email, Customer address |
| **Device & fault** | Device, Serial number ("series number"), Customer fault description |
| **Service / work** | Support admin, Labour hours, Spare parts |

`ID` is the internal record id — show it small (caption) or hide it; never the primary label. `Case number`
is the human identifier and the visual anchor.

### 6.2 Case Detail view (user-friendly layout)

- **Sticky header:** `Case number` (large, monospace) + **Status chip** + `Job type` and `Service order`
  as secondary. Right side: primary **Edit** action, overflow menu, and "Updated {relative time}".
- **Change banner (below header):** if fields changed since the user last viewed — "3 fields updated
  since your last visit", with a jump/clear action. (§8)
- **Body = tabs:**
  - **Overview** — the four sections above as **Material cards**, each a label/value list. Two columns on
    desktop (Customer + Device&fault side by side, Service/work below), single column on mobile. The
    fault description spans full width (long text). Dynamic fields render here per `field_definitions`.
    Recently changed fields get a subtle tonal highlight + "Updated" marker. (§8)
  - **Documents** — list, upload, download, delete.
  - **Activity** — comment thread; post, edit own, @mention.
  - **History** — chronological audit log; status changes visually distinct.
- **Empty/edit:** edit mode uses the same sections as a form with inline validation. Every save writes
  audit events and (where relevant) notifications.

## 7. Views / screens

### Auth
- **Sign in** — email + password (or magic link). Clear error and empty states.

### Global shell
- **App layout** — Material top app bar + left nav (Cases, Reports, Admin, Profile). Top bar shows the
  **notification bell with unread badge**, user + role, and active region/tracker context. Nav by role.

### Dashboard & reports
- **Dashboard (home)** — role-aware summary cards + a few charts: cases by status, cases by region/tracker,
  open vs closed over time, average labour hours, aging/overdue cases. Partners see only their tracker.
- **Reports** — simple filterable reports (by region, tracker, status, date range) with export [CSV?].
  Keep it simple: counts, breakdowns, and 2–3 charts. Not a BI tool.

### Cases
- **Case list** — table of cases the user can see. **Header shows the total count** of matching cases
  (e.g. "Cases — 128"). Columns: case number, status, region, tracker, job type, updated. Rows for cases
  with unseen updates are visually marked (dot/bold) + "Updated {time}". Filters: region, tracker, status,
  search. Sortable, paginated.
- **Case detail** — see §6.2.
- **Create / edit case** — sectioned form (§6.1) with stable + active dynamic fields the role may set.

### Notifications
- **Notification center** — dropdown from the bell + a full page: list of notifications (type, case,
  actor, time), read/unread, mark-all-read, click-through to the case. (§9)

### Admin (Portal Admin only)
- **Users** — list, invite/create, assign role + region(s)/tracker(s), deactivate.
- **Regions** — CRUD.
- **Service trackers** — CRUD; each assigned to a region; assign partner users.
- **Field definitions** — CRUD dynamic fields: type/options, per-role visibility, deprecate (no hard delete).

### Account
- **Profile / settings** — name, password, notification preferences.

### System states (every screen)
- Loading, empty, error, permission-denied are first-class.

## 8. Change awareness (how users notice updates)

Goal: a user should immediately see *what changed* and *where*, without hunting.

- **Per-user "last seen" timestamp per case** (a `case_views` table: user_id, case_id, last_seen_at).
  Compare `case.updated_at` / recent `case_events` against it to compute "unseen".
- **Case list:** unseen-update cases get a leading dot / bold row + "Updated {relative time}". Optional
  filter "Recently updated".
- **Case detail banner:** summarize what changed since last visit ("Status → In repair, 2 fields updated"),
  linking to the fields. Mark the case seen when opened.
- **Field-level highlight:** fields changed since last seen get a subtle tonal background + a small
  "Updated" chip; status changes are emphasized most. Derive changes from `case_events`.
- **Status is special:** always the most prominent change indicator (color + label), since it's the key
  business signal.

## 9. Notifications

- **Triggers (configurable later):** status change, new comment / @mention, assignment to you, new
  document, case created in your scope.
- **Delivery:** in-app first (bell + unread badge + notification center). Email later — out of scope now.
- **Model:** `notifications` (id, user_id, case_id, type, actor_id, payload JSONB, read_at, created_at).
  Written in the data layer alongside the audit event, respecting each recipient's scope/permissions.
- **Rules:** never notify a user about a case or field they can't see. Respect per-user preferences.
- **Realtime (optional):** Supabase Realtime can push new notifications live; polling is fine to start.
